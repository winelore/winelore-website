# WineLore page-loading investigation — 30 September 2026

The deployed site has measurable server latency and a second loading phase for identity metadata. These findings explain why the shell and its content arrive at different times. The exact delay in the user's authenticated session has not been captured, so token refresh remains a code-supported hypothesis rather than a measured cause of that session's slowdown.

The user identified https://www.thewinelore.com/competitions and reported testing while signed in. Measurements below were made without importing or changing the user's authentication cookies. Only public pages, GraphQL queries, and read-only holder metadata actions were requested. No application implementation changes or deployment were made. A local production build succeeded; its generated change to next-env.d.ts was restored.

This is a small diagnostic sample, not a percentile benchmark. First-call spikes are consistent with connection setup, function initialization, or upstream cache warming; the measurements do not isolate which of those caused each spike. API and HTML samples are separate requests and must not be added as if both occur on the same navigation.

1. **The application runs across the Atlantic for European requests.** Every sampled dynamic production response reported `x-vercel-id: fra1::iad1::…`. The request passes Frankfurt and executes the function in Washington, D.C. Vercel documents that this header includes both ingress and function execution regions: https://vercel.com/docs/headers/response-headers#x-vercel-id. This provides an explanation for the roughly 150–300 ms floor even on repeated small responses. Align the function region with the actual production API/database location and primary users. The production backend location itself was not established, so selecting Frankfurt must follow that check.

2. **Names and avatars load after hydration through separate server actions.** `app/competitions/CompetitionsClientView.tsx` calls `useUsernames`; the signed-in profile menu and mobile tab bar call `useCurrentUserAvatar`. Detail pages call both holder hooks. `app/userActions.ts` resolves names and avatars separately, and `packages/core/src/auth/displayName.ts` first resolves a variation, then fetches its name or avatar. The same variation lookup is duplicated across the name and avatar paths. Client caches and request deduplication are already present, but the two kinds of requests do not share their data. The deployed bundles contain those cache implementations.

   Next.js dispatches client-invoked server actions one at a time: https://nextjs.org/docs/app/getting-started/mutating-data. The first measured name and avatar calls together occupied about 1.19 seconds of sequential request time. On a signed-in list, the avatar usually belongs to the current user and the names belong to holders, so that total illustrates the request pattern rather than an exact measurement of the user's session. Prefer a cached route handler for batched public identity reads, returning name and avatar together and allowing independent page reads to run concurrently. Keep mutation actions for writes.

3. **Page content is refetched on navigation.** `app/competitions/page.tsx:4` forces dynamic rendering; the GraphQL transport in `lib/apiClient.ts` uses `cache: 'no-store'`. The list waits for its query before returning its client view. Links can prefetch the loading shell, but the default partial prefetch of a dynamic route does not imply the complete content has been fetched: https://nextjs.org/docs/app/guides/prefetching. Use brief caching and targeted invalidation for data that tolerates it, scoped by actor wherever responses vary by user. Avoid putting private or live scoring data into a shared public cache.

4. **Authenticated refresh can block navigation on cosmetic work.** `proxy.ts:42` awaits `refreshTokens`; `packages/core/src/auth/session.ts:48` awaits display-name resolution before completing the refreshed session. That adds two identity queries after the token exchange. Those fetches and the OAuth fetch have no explicit application timeout. The proxy matches pages, server actions, and API requests, so simultaneous requests near expiry can each attempt refresh. Preserve the existing display name during refresh, bound upstream waits, and deduplicate concurrent refreshes where feasible. This path needs a timing trace during an actual refresh to quantify its contribution.

5. **Competition detail pages repeatedly enter the action queue.** `app/competition/[id]/CompetitionClientView.tsx:289` polls the entire competition and up to 50 commissions every three seconds for every status except COMPLETED. The loop does not pause when the document is hidden. That creates 20 read actions per minute per open detail tab, including draft and planned competitions. Restrict frequent updates to states that need them, pause hidden-tab work, and move reads to a query endpoint or events with a slower fallback.

6. **Other signed-in pages still have expensive scans.** `app/myCommissions/page.tsx:34` walks every commission page sequentially, then filters and paginates locally. Every pagination navigation repeats that scan. The home page already runs its independent panels concurrently, but its commission panel can still scan multiple pages; the entire Promise.all must finish before HomeClientView appears. An API member filter/count is the lasting fix. Independent server-component panels with Suspense would let the useful dashboard sections appear before its slowest panel finishes.

The deployed competitions page references 18 JavaScript bundles, totaling approximately 1.15 MB decoded or 349 KB when locally gzip-compressed. These are size estimates, not measured network transfer totals; production serves Brotli. Its GraphQL registry is approximately 74 KB decoded. There is room to trim initial client code, but the measured request chains and geographic latency are stronger evidence than bundle size alone.

The workspace changed during inspection. Early reads showed button-based navigation, plain personal-menu anchors, sequential dashboard requests, and no client username cache. Later reads at commit e4e315a showed these had already been corrected. Deployed browser navigation is also composed of links, and deployed bundles contain the username/avatar caches. Those earlier findings should not be treated as outstanding bugs. The source links above refer to the later code.

Recommended order: check function/backend regional placement; combine identity metadata reads; add safe caching and targeted content prefetch; remove cosmetic work from the refresh critical path; reduce polling and backend scans. Capture a signed-in browser network trace during the reported slowdown to distinguish ordinary navigation from token refresh and action-queue waiting before attributing all delay to a single cause.
